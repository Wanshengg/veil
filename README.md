# veil — экспериментальный туннель «под TLS-сайт»

Свой протокол на 5 пользователей, задача — измерить, сколько он проживёт под ТСПУ.
Клиентский софт не пишется: `veil-client` поднимает локальный SOCKS5, поэтому
подходит любой браузер/приложение.

## Что внутри

```
TLS 1.3 (реальный сертификат, ClientHello Chrome через utls)
 └─ [VEIL][ver][ts:8][salt:16]        ← 29 байт заголовка
     └─ AEAD-кадры: len(4) | nonce(24) | XChaCha20-Poly1305(2-byte payload len | payload | random pad 0..16)
```

- Ключи: HKDF-SHA256(PSK, salt) → отдельные ключи в каждую сторону, salt в открытом виде.
- Защита от replay: salt в LRU на 10 минут, окно timestamp ±120 с.
- Первое, что видит DPI: обычный TLS 1.3 ClientHello Chrome (JA3 ALPN `h2,http/1.1`).
- Fallback: всё, что не начинается с `VEIL`, прозрачно уезжает на реальный сайт
  (`-fallback`), включая уже прочитанные байты. Активное зондирование видит живой HTTPS-сайт.

## Что проверено (реальные прогоны, не «должно работать»)

| Проверка | Результат |
|---|---|
| HTTP через туннель (SOCKS5) | ok |
| Обычный HTTPS-клиент на :8443 видит fallback-сайт | ok |
| Сырой мусор на :8443 (не TLS) | отдаётся fallback-страница |
| 1 MiB через туннель | sha256 совпал побайтно |
| Внешний интернет через туннель | ok (`example.com`) |
| Набор TLS-шифров/кривых/ALPN vs реальный Chrome 145 | совпал полностью |
| Отпечаток | `t13d1516h2`, у Chrome 145 — `t13d1517h2`: не хватает одного расширения (`51764`), utls 1.8.2 соответствует Chrome 133 |

Перепроверить: `bash scripts/test_local.sh` и `python tools/ja3check.py chrome`.

## Чего пока нет

- SNI/ASN-консистентности: сертификат должен быть на ваш домен, домен — на ваш IP.
  `-sni` у клиента обязан совпадать с CN/SAN сертификата.
- HTTP/2 в fallback: сервер отдаёт `http/1.1` (как nginx без h2); ClientHello при этом
  рекламирует `h2` — это норма для nginx-конфига, но не идеал.
- UDP (QUIC, звонки) — только TCP.
- Мультиплексирования нет: одно SOCKS-соединение = одно TLS-соединение (для 5 человек ок).
- Настоящего замера под ТСПУ ещё не было.

## Сборка

```bash
go build -o bin/veil-server ./cmd/veil-server
go build -o bin/veil-client ./cmd/veil-client
go build -o bin/gencert     ./cmd/gencert        # только для локальных тестов
```

## Сервер (VPS)

```bash
# 1. реальный сертификат на домен, указывающий на этот IP
certbot certonly --standalone -d veil.example.com
# 2. nginx (или любой сайт) на 127.0.0.1:8080 — то, что увидит зонд
# 3. запуск
./veil-server -addr :443 \
  -cert /etc/letsencrypt/live/veil.example.com/fullchain.pem \
  -key  /etc/letsencrypt/live/veil.example.com/privkey.pem \
  -psk  'длинная-случайная-строка' \
  -fallback 127.0.0.1:8080
```

Автоустановка: `deploy/install.sh` (systemd, отдельный юзер, CAP_NET_BIND_SERVICE).

### Ключи и права получателя

Клиентский ключ — только PSK для туннеля. Получатель ключа не получает ни
SSH-аккаунта, ни оболочки, ни sudo:

- `veil` — системный пользователь с `nologin`; `install.sh` дополнительно
  выкидывает его из группы `sudo`, если кто-то туда добавил;
- `/opt/veil/keys.txt` — `root:veil 640`: сервис читает, писать может только root;
- выдача/отзыв ключа — правка файла + `systemctl reload` (SIGHUP), соединения
  не рвутся;
- юнит в песочнице: `NoNewPrivileges`, `ProtectSystem=strict`, `PrivateDevices`,
  `RestrictSUIDSGID`, `LockPersonality`, `ProtectKernel*`,
  `RestrictAddressFamilies` (`systemd-analyze security` → 4.3 OK).

Проверка на живом сервере: `sudo -u veil test -r keys.txt` — да,
`sudo -u veil bash -c 'echo x >> keys.txt'` — нет,
`ssh veil@127.0.0.1` — `Permission denied (publickey)`.

### SSH к серверу через туннель

Клиент поднимает SOCKS5 на `127.0.0.1:1080`. Если ходить на сервер напрямую
нельзя или не хочется светить домашний IP:

```bash
ssh -o ProxyCommand="python tools/socksbridge.py %h %p" root@SERVER
```

`tools/socksbridge.py` — мост SOCKS5 → stdio, только stdlib.

### Пул серверов (несколько серверов по одному ключу)

Список серверов лежит на отдельном «скучном» хосте и отдаётся зашифрованным
блобом, чтобы хостинг и случайные сканеры не видели ни списка, ни формата.

```
pool/pool.json                  — исходник (в приватном репозитории)
dist/pooltool.exe keygen        — пара подписи Ed25519 (приватный ключ дома, не в git)
deploy/pool-push.sh             — подписать + зашифровать + выложить, напечатать URL
```

Формат файла:

```
"VLP2" | nonce(12) | AES-256-GCM( bodyJson + "\n" + base64(ed25519(bodyJson)) )
ключ = HKDF-SHA256(psk, salt "veil-pool-v2", info "blob")
```

Почему так: PSK уже есть в ключе клиента, поэтому отдельного секрета не нужно;
подпись защищает от подмены файла на хостинге; снаружи файл — 484 байта мусора.

Своя подписка у любого пользователя: в ключе можно указать публичный ключ
своего пула (`|pk=<base64>`). Если он есть — подпись проверяется им, и
приложение не нужно пересобирать. Без `pk` используется встроенный ключ
(официальный пул).

Проверка (реальный прогон): скачали блоб по HTTPS → `pooltool unpack` расшифровал,
подпись сошлась, JSON совпал с исходником; испорченный байт и чужой PSK — отказ.

Хост раздатчика не содержит ничего, кроме nginx и статики:
`/var/www/api/static/data/<32 hex>` с `application/octet-stream`, `access_log off`,
`X-Robots-Tag: noindex`, без листинга каталога.

## Клиент

```bash
./veil-client -socks 127.0.0.1:1080 -server veil.example.com:443 \
  -sni veil.example.com -psk 'та-же-строка' -fp chrome
```

Дальше SOCKS5 `127.0.0.1:1080` в браузере или в любом приложении.
`-insecure` — только для самоподписанных тестов.

## Замер выживаемости

```bash
python tools/probe.py -server veil.example.com:443 -sni veil.example.com \
  -psk '...' -interval 300 -log probe.jsonl
```

Каждые 5 минут: TLS-доступность порта, запрос через туннель, задержка, объём.
По JSONL считается время до первого сбоя — это и есть «сколько прожил».

Найдено на живом трафике:

- Chrome-подобный ClientHello начали резать волнами (firefox/safari/edge проходили),
  поэтому клиент перебирает отпечатки и запоминает рабочий;
- браузеры читают `socks=` из WinINET как SOCKS4 — клиент теперь поддерживает SOCKS4/4a

мультиплексирование. Ключи доступа (`veil://…`) в репозитории не хранятся.

## UDP (база для TUN)

Кадры туннеля теперь переносят и датаграмы: `addrlen | addr | port | payload`.
Клиент отвечает на SOCKS5 `UDP ASSOCIATE`, сервер держит по сокету на адрес и гоняет трафик
в обе стороны. Проверка: DNS-запрос в 8.8.8.8 через туннель — `tools/test_udp.py`
(ответ `id=0x1234 answers=2`, 12 мс локально). Это то, без чего TUN ломал бы DNS и QUIC.

Не сделано: сам TUN (wintun + маршруты, нужны права администратора) и фильтр по процессам.

## TUN — статус: экспериментально

`veil-client -tun` создаёт адаптер `veil` через wintun, поднимает tun2socks и уводит
`0.0.0.0/0` в туннель, оставляя `/32` на сервер через физический шлюз.

Проверено: адаптер создаётся, маршруты встают, запросы уходят в туннель
(`tunnel -> 1.1.1.1:53` в логе), сеть восстанавливается после остановки.
**Не работает: обратный путь** — ответы из netstack не доходят до сокетов приложения,
поэтому TUN-режим пока не включается в интерфейсе. Требует администратора.

## Порт: 443 блокируется по волнам, рабочий — 8443

ТСПУ режет не IP, а конкретный порт: к `203.0.113.10:443` TCP-соединение
устанавливается, но ClientHello до сервера не доезжает (в логах сервера —
`tls handshake: read ... i/o timeout`), при этом `:8443` с тем же сертификатом
и тем же SNI проходит и верифицируется.

Как проверить за минуту:

```bash
# временный TLS-листенер на запасном порту
openssl s_server -accept 8443 -cert fullchain.pem -key privkey.pem -www -quiet &
# если здесь handshake проходит, а на :443 висит — режут порт, а не адрес
openssl s_client -connect 203.0.113.10:8443 -servername se.example.com </dev/null
```

Переезд: `-addr :${VEIL_PORT:-8443}` в юните, `ufw allow 8443/tcp`,
и новый порт в `veil.ini` + в `veil://` ключах (payload — base64 от
`server:port|sni|fp|psk`).

## Перебор портов (обход волн блокировки)

ТСПУ блокирует не только адрес, но и конкретные порты, причём волнами: в один
час живёт `:443`, в другой — только `:2083`. Поэтому:

- сервер слушает сразу несколько портов: `-addr :443,:8443,:2083,:9443`;
- клиент держит список (`-ports 443,8443,2083,9443`) и при таймауте
  перебирает их по кругу, запоминая рабочий:

```text
порт se.example.com:8443: read tcp ...: i/o timeout
порт se.example.com:8443 не прошёл, работаю через se.example.com:443
fp chrome tls1.3 ok
```

После первого успеха остальные соединения идут сразу на рабочий порт.
